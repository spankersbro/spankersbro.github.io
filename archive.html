Featured build

An orchestration agent that tries to solve your problem before escalating it to a person

Built an AI agent, plus two purpose-built subagents, that helps colleagues with day-to-day company-tool problems — first searching an internal knowledge base and the web for an existing answer, then escalating by name to the actual person responsible if that doesn't resolve it. Orchestrated entirely on the company's internal agent-orchestration platform; the underlying tools and integrations are the platform's, the orchestration design and instruction text are what I built.

  1. Self-help first, always disclosed. A knowledge-retrieval subagent checks an internal ticket system for a known fix, falling back to a general web search if nothing matches — and the main agent always states where an answer came from, even when someone explicitly asked to be routed straight to a person.
  2. Root-caused real integration bugs, not just prompt tweaks. Several of the underlying issue-tracker's write actions were silently failing or returning wrong results — enum and assignee fields needed structured values instead of plain text, one optional parameter had to be omitted rather than passed empty, and a "return only these fields" option was breaking basic searches. Fixed by testing directly against the API surface until the actual contract was confirmed, not by guessing.
  3. The right subagent, only when actually needed. Escalation only fires if the employee is still stuck after seeing what self-help already found — and it hands off to a colleague by name with a direct message and a tracked ticket, not a channel post that gets lost.
  4. Security reviewed before rollout. Added a pre-publish check for least-privilege access, scoped conversation handling, and sanitized knowledge-base content — treating a support agent with write access to internal systems as something that needs a review, not just a demo.

The interesting failure mode wasn't the AI reasoning — it was a nested subagent needing to ask a human for permission mid-task with no human actually present in that call. That shaped which actions live on the main, human-facing agent versus a subagent, more than any prompt-engineering choice did.

Featured build

The test-suite migration, phase two: from migrated to actually trusted

Last cycle's migration got every module speaking one test format. This phase went after what that migration didn't fix on its own: parts of the suite were still partially skipped and non-blocking in CI, quietly hiding bugs of their own — 230 commits over three weeks turned that into a required, fully green gate.

  1. Transactional isolation, not manual cleanup. Built a PHPUnit extension that wraps every test in a rolled-back transaction, replacing thousands of lines of hand-written cleanup code across the whole suite.
  2. Un-skipping is how you find out what's actually broken. Eighteen previously-disabled tests came back online — and several had been quietly hiding real bugs, including a database reconnect that silently dropped the session timezone on every request.
  3. Order-dependent tests, exposed. A transaction-savepoint depth leak on skipped tests, and tests that only ever passed because of the order they ran in — both invisible until the isolation work forced them to run standalone.
  4. A gate, not a suggestion. The suite moved from non-blocking to a required CI check — it now has to stay green, not just exist.

The migration itself moved the format; this phase is what made the result something you can actually rely on — a suite that fails loudly instead of one that quietly stops meaning anything.

Featured build

Reworked client numbering end-to-end to support alphanumeric IDs — while it was still moving underneath

An enterprise client running SAP alongside TEAMBOX needed the same alphanumeric client codes in both systems — a change that touches nearly everything client-numbering ever touches: two frontend stacks, a decades-old payment-reference format, and the assumption, baked in for years, that a client ID is just a number.

  1. Moved the field once the domain model demanded it. The new external-ID field started on the company record, then moved to the client record mid-build once that became the obviously correct owner — the kind of correction that's cheap early and expensive if you wait.
  2. Decoupled the parts that used to be tangled together. A new per-client job-number pattern engine separates project numbering and payment references from the new external-ID format, instead of leaving them implicitly coupled to "the client number is numeric."
  3. Immutable once set, on purpose. The external ID locks after creation to guarantee uniqueness — a constraint added deliberately, not a limitation discovered later.
  4. Caught its own regressions before anyone else did. A literal external ID of "0" was being treated as unset, and client search silently broke the moment IDs stopped being purely numeric — both found and fixed in review, before either could reach a real client.

Still in progress, behind a feature flag, with a permanent end-to-end test suite added alongside it — the kind of change where "ship it behind a flag and watch closely" is the responsible call, not a hedge.

Featured build

Enforcing one path for schema changes surfaced a run of bugs that would have broken real deployments

Making a proper schema-migration tool the only way schema changes happen — no more parallel legacy upgrade paths — turned up problems the old tooling had been quietly getting away with for years.

  1. A flag that had never worked. The legacy upgrade tool's CLI flag parser had no working long-form flag at all — a bug invisible for as long as everyone happened to use the short form.
  2. A crash on every real run. One of its flags crashed on every actual execution — not an edge case, the normal path.
  3. A subtle auth mismatch. CI database authentication was failing from a password-decoding mismatch between the old credential convention and a newer one — the kind of gap that only shows up once both conventions exist at the same time.
  4. Cleanup with a paper trail. Fifteen historical legacy upgrade directories deleted once confirmed superseded, and the migration strategy now lives as an architecture decision record that gates schema-change review going forward — not just tribal knowledge.

None of these bugs were the point of the migration — they were what the migration had to survive finding, on its way to becoming the one real path for schema changes.

Featured build

Rewrote the PHP test suite from the ground up — and it kept finding real bugs

Migrated the entire PHP test suite to Pest 3 across two dozen modules, collapsing a custom dual-runner setup — separate "live" and unit test classes, two bespoke base classes — into one unified test format. The line count went down once duplicate test variants were folded together, but nearly every module gave up at least one previously-invisible bug the moment its tests stopped running in isolation.

  1. One test format, not two. Every module's paired live/non-live test classes merged into a single Pest-style file, retiring two custom base classes that existed only to work around the old split.
  2. Merging exposed what isolation had been hiding. A field-cache poisoning bug that crossed module boundaries, several mock/real class collisions, and a shared-state bug quietly affecting dozens of test files — all surfaced only once the tests ran together instead of apart.
  3. Logged for continuity, on purpose. Every fix and decision recorded in a running delivery doc, because a rewrite this size can't live entirely in one person's head across weeks of work.
  4. Verified module by module, not just declared done. Each migrated module re-run against the full suite before being marked complete, so "the tests pass" still meant what it meant before the rewrite.

The rewrite itself is done across all two dozen modules. The bugs it surfaced weren't the point of the exercise — but they were the real payoff.

Featured build

Replaced an entire bespoke migration system with Doctrine — and caught a CLI flag that had never worked

Built and shipped, solo, a full replacement of a homegrown YAML-driven schema and upgrade system with Doctrine Migrations: hundreds of YAML schema files and legacy upgrade scripts, plus several schema classes, deleted outright — a net reduction of thousands of lines across hundreds of files, as one continuous piece of work. Along the way, found that the CLI framework's long-flag parsing had never actually worked anywhere in the codebase, silently falling back to defaults instead of erroring out — an untrimmed-whitespace bug that had gone unnoticed for years behind a short-flag fallback path, the kind any long-lived codebase accumulates.

  1. A replacement, not a patch. The old DatabaseSchema/TableSchema system and its YAML fixtures are gone; a FixtureManager and Doctrine Migrations now own schema and test-database setup end to end.
  2. More reliable than what it replaced. Added MySQL reconnect-on-disconnect handling and an advisory lock around the baseline-migration guard — failure modes the old system simply didn't defend against.
  3. Fixed with a regression test, not just a patch. The long-flag parsing bug got a test that pins the correct behaviour down, so it can't silently regress again.
  4. A real deployment blocker, found and closed. Old-system installs couldn't mark the migration baseline as applied because the metadata storage table didn't exist yet — the kind of gap that only shows up the first time someone actually runs the migration for real.
  5. Chased an intermittent CI failure to the actual cause, then cleaned up with confidence. Went through retry logic, then in-process table drops, before landing on the real fix: reusing a single shared database connection instead of opening a new one per test. Fifteen historical legacy-upgrade directories were deleted only once their behaviour was confirmed already migrated, and staging-scenario migrations were deliberately written and reverted before merge as a test method, not leftover cruft.

Deleting a bespoke system wholesale and rebuilding it on Doctrine is what made this migration pipeline fundamentally different from what came before — the flag parsing, table-existence checks, and connection reuse are what made it safe to actually run against production.

Featured build

An agent that triages its own production logs

Most "AI wrote some code" stories stop at code review. This one runs unattended against production. Once a week, a Claude Code command connects to our log aggregator, pulls the highest-volume error patterns, and works through them like a careful on-call engineer would — not a script that just counts lines.

  1. Fingerprint and dedupe first. Every distinct error pattern gets a stable fingerprint, checked against existing tickets by full-text search before anything new gets filed — so a recurring error creates one ticket, ever, not fifty.
  2. Investigate before filing. Before opening a ticket it locates the actual source line, reads the surrounding code, checks whether the same pattern exists elsewhere in the codebase, and looks at git history to see if a fix is already in flight. The ticket ships with a concrete before/after code suggestion attached — not just a stack trace for someone else to decode later.
  3. A dashboard that doesn't oversell itself. Every run regenerates a live status page: colour-coded severity, before/after volume bars, a trend badge per issue. When a pattern stops firing, it's labelled silent, not fixed — silence isn't proof of a fix, and the tool doesn't get to claim credit it hasn't earned.
  4. Verify, don't assume. A separate verify mode re-checks the log volume after a deploy to confirm a fix actually worked, instead of treating "ticket closed" as the end of the story.

The hard part wasn't the log analysis — it was making it deterministic. The same command, run by a different AI session or a different teammate months from now, has to produce the identical dashboard from identical inputs. That meant writing out the exact fingerprint algorithm, the exact API quirks, and the exact layout rules as if onboarding a new engineer with zero context, because in practice, that's exactly what it is.

Featured build

A KPI dashboard the team actually trusts

Sprint retros used to run on gut feel and whichever ticket someone happened to remember. This is a Claude Code command that turns raw ticket history into a dashboard the team actually opens — not because it's flashy, but because two rounds of "that number's wrong" feedback got taken seriously and fixed instead of explained away.

  1. Correct attribution, not just counting. Bounce rate — how often a ticket ping-pongs between developer and reviewer — is attributed to whoever actually owned the ticket at the time, including mid-sprint handoffs, and a QA rejection is never mistakenly pinned on the person doing the rejecting.
  2. Numbers scoped to what actually happened. Off-board tickets, work outside the sprint window, and scope changes are filtered deliberately: a 48-hour grace window separates ordinary sprint-planning carryover from genuine mid-sprint scope creep, so the metric means what it says instead of what's convenient.
  3. Built on real feedback, not first-draft numbers. Two rounds of team pushback led to real rework — splitting QA bounces from review bounces, adding a ±20% estimation-accuracy band, showing planned-vs-logged time only for developers who actually worked the sprint — not cosmetic polish.
  4. The same rigor as the log-triage tool: reproducible by design. Deterministic sorts, plain standard-library Python, no hidden state — the same sprint, run twice, produces the same numbers. A dashboard that gives a different answer depending on who ran it isn't a dashboard, it's a rumor.
  5. A third round, months later, still holding up. Split the review/QA bounce metric further, added FTE-progress tracking, and reworked a process-adherence rule that had started producing misleading verdicts — proof the first version wasn't a one-off, it's a tool people keep pushing back on because they keep using it.

Some of it was about restraint, not features: a stacked-bar chart got built, tested against real data, and then dropped because its rounded segments visually misrepresented small proportions. The donut chart stayed; the flashier option didn't make the cut.
