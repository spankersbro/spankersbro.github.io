A Runtime Upgrade That Would Have Moved Amounts by a Cent: Guards That Make a 448-File Change Safe

A rounding change that moves money, the tests that keep it out, and the test that caught two new calls on the day of the merge.

November 2026 · Runtime upgrade

The advisory bars are to scale.

Why it had to happen now

Security support for PHP 8.2 ends on 31 December 2026, and the product ran on it. So the upgrade to 8.5 had to land before the end of the year, and before my last day. A colleague had started it: their upgrade commits and their rounding tests are in the final pull request and keep their name. I brought the work together into one landing and took it through review.

The trap: a half cent

Most of an upgrade like this is routine: new types, removed functions, updated libraries. One change is not. From PHP 8.4, rounding a computed value that ends in a half cent can go down instead of up. 2.50 × 1.19 is 2.975, and that now rounds to 2.97 instead of 2.98.

In an ERP that writes invoices, that is not a detail. The decision, made with the people responsible for the product, was to keep today's results exactly.

Three guards

  • One helper for all rounding. All 206 rounding and number-formatting calls, in 101 files, now go through one helper that returns what PHP 8.2 returned. No signature changed. While the code still ran on 8.2, a test compared the helper with the built-in functions on 20,000 values.
  • A new native rounding call fails a test. The helper only works if nobody goes around it. So a test scans the code and fails on any new call to the built-in rounding functions.
  • A new deprecated call fails a test. The same idea for the calls PHP 8.5 marks as deprecated, so the next upgrade does not start with a backlog.

The library updates followed one method: tests first on the old version, one library at a time, the full suite after each. The dependency audit listed 34 security advisories before and one after, low in severity and tracked in its own ticket.

One landing

The work had grown into three stacked pull requests: rounding, runtime, libraries. They landed as one, so the main branch never ran a half-upgraded state. 448 files changed. The full backend suite passed on PHP 8.5: 20,895 tests, none failed.

An automated reviewer went over it in two passes, plus two review-only pull requests for the files its first review did not list. It found one thing, which was fixed. A colleague approved the merge.

Two changes users can see are written down in the pull request instead of discovered later. A spreadsheet import reads a time cell at exactly half a second one second lower. And a broken sign-in cookie is now rejected instead of causing a server error.

The guard on merge day

The pull request was merged at 09:12. Shortly after, the main branch was red: the rounding test had found two new native calls. Two other pull requests had added them after this one's last CI run, and the branch rules did not require an up-to-date branch before a merge. So none of the three checks had seen the combination.

The fix was two lines: both calls go through the helper. It was merged at 10:24. Without the test, those two places would have rounded differently from the rest of the product, quietly, by a cent.

What I take from it

  • A rule that is not checked is a wish. "Always use the helper" would not have survived a week. A test that fails did not survive the first hour.
  • Land big changes as one. Three stacked pull requests are easier to review. One landing keeps the main branch in a state that was actually tested.
  • Credit stays with the work. The commits of the colleague who started it keep their name. The agent did a lot of the volume; the decisions on rounding and on what users see were people's.
