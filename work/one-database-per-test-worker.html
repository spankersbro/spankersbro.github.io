Every End-to-End Test Worker Gets Its Own Database: Reset in Milliseconds, and the Isolation Code Is Gone

Shared test data made every spec carry cleanup code. One database per worker, reset before every test, removed it, and found two real bugs on the way.

November 2026 · Test infrastructure

The reset that runs before each end-to-end test.

Why shared test data was the problem

Our end-to-end tests drive a real browser through the product, and all of them used one database. So every spec had to protect itself and the others: clean up after itself, restore what it changed, give records unique names, avoid the seed data other specs relied on, sometimes create its own users. When that code missed something, a later test failed for no reason of its own.

It also kept the suite from running fully in parallel: the tests in one file had to run one after another. This was the last step of a month spent on the suite's reliability; the story of that month is in The Agent Wrote Flaky Tests Too.

How it works

  • One database per worker. Each test worker gets its own copy of the seed data. A cookie sends the worker's requests to its own application processes, so one worker never sees another's data. Without the cookie, the application behaves as before.
  • Reset before every test, in milliseconds. Copying a whole database before each test would be far too slow. So database triggers note which tables a test wrote, and the reset copies only those back. On average that took 26 to 44 ms per test.
  • The same everywhere. One script seeds the databases, the same way in CI and in the development container. A developer's own database is never touched.

What the specs no longer need

With a clean database before every test, the isolation code had no job left. The specs lost their cleanup, their restores, their unique names, their rules about the seed data and most of their own users. Full parallel runs are on. 21 old tests that other test layers already covered were removed. The change removed more lines than it added: 4,887 in, 5,360 out.

To keep it that way, the instructions for the automated code reviewer now check new specs against the new rules: no cleanup code, state set up inside the test, no extra users unless a test needs other rights.

Two real bugs found on the way

Four fixes came out of the work, each with a failing test first:

  • Unsaved input could disappear. A layout read that arrived late rebuilt a dashboard grid and dropped what the user had typed. The same code is used on the project, person and company pages.
  • A new list column stayed empty. After adding a column to a list, the list did not load its rows again, so the new column showed nothing until a reload.
  • Two smaller ones. A table was cleared with a statement that silently committed any open transaction. And in development, a missing class made the loader rescan 3,845 files on every request.

The proof

After the final merge of the main branch, on the local CI stack with four workers: all 370 tests passed. Then every test three times: 1,110 of 1,110 passed, no flaky test, in 14.5 minutes. The backend suite passed too: 21,231 tests. The flaky tests that showed up during the work were fixed at their cause, in five specs.

Known limits

  • A request that the previous test left running can still write after the reset.
  • Files in storage are shared by all workers, and record counters are not reset.
  • One list setting that is stored per browser tab survived the reset. Three specs work around it with a tab of their own. The cause was not found.

What I take from it

  • Fix the setup, not each test. All that careful cleanup code went away with one change to how tests get their data.
  • Test work finds product bugs. Two of the fixes were real bugs for users, not test problems.
  • Write the limits down. The pull request lists what the reset does not cover, including one thing nobody could explain yet.
