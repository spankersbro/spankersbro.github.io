Eleven Pull Requests in One Day: Agent Skills That Make the Right Decision Cheap

Three agent skills from my daily work: what each one does, the numbers behind it, and where a person still decides.

October – November 2026 · Three agent skills

Bar lengths are to scale only roughly: one working day against about five and a half.

Why I write agent skills

An agent skill is a written procedure an AI agent follows, with small scripts for the parts that must never vary. I write one when a task is repeated, risky, or blocked on something only one person knows. The skill carries that knowledge, and its refusal rules carry the caution.

Below are three from October and November 2026, in the codebase I have worked on for twenty years. Every number comes from a pull request, a commit or a CI run, except one estimate, which is marked as mine.

1. Eleven pull requests in one day

Our end-to-end tests lived in their own repository, so a feature and its test could never change in the same commit. My first fix was a workaround that pinned each branch to a version of the tests. Three times, a pin slipped into the main branch through a squash merge and broke it. I decided to stop patching the workaround and remove the reason for it: move the tests into the application repository.

The move itself was simple. The open work was not. Eleven test pull requests were still in progress in the old repository. By hand, each would have taken me about four hours: rebase onto the new layout, resolve conflicts, check the screenshots. That is about 44 hours, and until each one moved, its author was stuck.

So before the cutover I wrote a script and an agent skill that port an open pull request into the new layout:

  • Three-way, binaries included. The obvious tool, a plain diff, leaves out binary files, and the visual test baselines are PNG screenshots. The script applies the pull request's changes against the commit the tests were copied from, screenshots included.
  • A conflict stops it. It marks the conflicting files and commits nothing.
  • A person approves every write. The skill asks before it merges the main branch, before every commit and before every push.
  • The old mistake cannot come back. CI now fails a feature branch that still carries a pin.

The cutover pull request, about 11,900 lines, was opened at 09:57 and merged at 20:08 on 3 November. All eleven open pull requests were ported the same day.

2. Testing a slow-query fix without a customer's database

Some bugs only appear with a customer's volume of data. QA cannot test those fixes on a small test system, and a customer database is not something QA should have. So fixes waited, or went out with a developer's word as the only test.

This skill walks from the ticket to a QA hand-off: find the expensive query, seed a staging copy, generate data in the right shape, measure the old and the new code on the same data, hand QA a one-click case, clean up. The interesting part is what it refuses to do:

  • Seeding runs only on a staging copy, and only when it is given that installation's own identifier. A missing or wrong identifier stops it.
  • The generator asks for an explicit YES before it writes, marks every row it creates, caps the number of rows, and refuses to run again while marked rows still exist.
  • Every query it runs is capped at 60 seconds. Measurement runs each query twice and reports the warm run, so caching does not flatter the fix.

The refusals were tested on purpose: without YES, over the row cap, with a real timeout and with an SQL error.

3. What review keeps sending back

Tickets came back from review for the same reasons again and again. I sorted 299 review comments and 22 bounces from seven weeks into kinds, and turned each kind into a question the agent must answer, with evidence, before a person looks at its work. The method is in Review History as a Checklist.

The skill takes a ticket of any type through the team's gates to human review. It reuses the existing bug-fix and triage skills instead of copying them. Every write, whether a comment, a state change, a push, a pull request or a branch delete, waits for a yes. The skill itself went through nine rounds of fresh review; the last one found nothing.

What the agents did not fix

CI time. Our five CI runners share one machine. Over 25 successful runs on the main branch, the same end-to-end suite took between 11 and 30 minutes, and the same runner took 11 minutes in the middle of a quiet day and 26 in a busy morning. That is load, not test count. Moving checks into faster test layers helps, but the real fix is capacity, and that is the next problem.

What I take from it

  • The agent did not make the decision. Moving the tests was my call. The skill made the right call cheap enough to take in one day instead of a week.
  • The refusals are the product. Each skill is mostly a list of things it will not do without a person: write to the wrong system, commit through a conflict, push without a yes.
  • Numbers get checked, not repeated. While writing this up I found a claim that the suite ran in under five minutes. It was the title of a ticket, not a result. It is not on this page.
