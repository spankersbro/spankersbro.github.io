A Finance Report From 18 Seconds to 2: Measure First, Move One Condition, Prove the Rows

Where the time went, the one condition that fixed it, and how I proved the report still shows the same rows.

October – November 2026 · Performance

The report's query on a copy of one customer's data. Bars to scale.

Where it started

One customer's valuation report, a finance overview of work in progress, took about 20 seconds to load. The median in the production access log was 19.6 seconds.

I worked on it with an AI agent, under the same rules as every change: measure before changing anything, write a failing test first, and prove the result on real data.

Measure first

The query plan, run with real timings on a copy of the customer's data, answered the question at once. Of 18.2 seconds, 16.0 went into three columns: the latest comment, who made the valuation, and when.

All three come from the same lookup: find the newest valuation entry for each row. That lookup is a subquery, and its filter pointed at the outer row instead of at its own table. So the database could not use the index built for exactly this lookup. It read all 6,778 valuation entries once for every row of the report.

The cause was old. The lookup came with a much earlier change, and nobody had measured it with this much data behind it.

One condition moved

The fix is one condition in a different place: the subquery now filters its own rows, and the outer query keeps its filter as before. Nothing else in the report changed.

  • A failing test first. A new test checks that the lookup can use the index and that the columns show the newest values. On the old code, two of its four cases failed.
  • Measured on generated data. With 27,840 generated entries, the three columns went from 3.3 seconds to 0.13.
  • Measured on the customer's data. On the copy, the whole query went from 18.2 seconds to 2.3.

Prove the rows

A faster query that returns different numbers is a new bug in a finance report. So the old and the new query ran against the same copy and their results were compared row by row: 276 rows, none different.

One case does behave differently, and it is written down as a decision instead of hidden. A task that also has a newer entry of another kind, which only the API can create, now shows its own values instead of empty columns. That is the correct value, and the pull request says so.

What it did not cover

There is no end-to-end test for the speed. The test data is far too small to show the difference, and the feature is off there. The backend test covers the values and the index. The time in the browser was to be checked after the release.

What I take from it

  • The plan names the cause. Guessing would have started with caching or a bigger server. The plan pointed at three columns and one subquery.
  • Speed is not the proof. The proof is the same rows. Without the comparison, this would only have been a faster report.
  • Small fixes need the same rules. A one-condition change got a failing test, two measurements and a written decision. That is what made it safe to ship quickly.
