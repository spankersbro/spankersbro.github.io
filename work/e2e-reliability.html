The Agent Wrote Flaky Tests Too: Turning Its Mistakes into Rules

Two weeks of end-to-end test work with an AI agent. It did the volume. It also made mistakes, and most kinds of mistake became a rule that the next test had to pass.

4 – 17 November 2026, numbers to 26 November · End-to-end tests, an AI agent and the rules between them

The loop that did the work. The agent supplied the volume; the rules kept its output honest.

Where it started

The end-to-end tests drive a real browser through a twenty-year-old product. Between 1 October and 3 November, 61 of the 131 runs on the main branch with a test report had a flaky test: one that failed and then passed on its retry. The retry made the run green anyway.

The suite was also slow, and the first thing to settle was why. A plan to split the slowest test files ended early: from CI data, the agent showed that a perfect split would save under a minute. Later measurements showed the real cause. The same 395 tests took 9.5 minutes on a quiet CI runner and 27.5 on a busy one. The same build took 4.6 minutes on my machine and 18.5 in CI. Most of the slowness was runner load, not the tests.

So the goal became two things: every check in the right test layer, and a suite whose green means something.

Who did what

I decided what good looks like, and where the limits were:

  • Decide, don't defer. The agent first left misplaced tests to "each author's call". I overruled that: we decide which layer a check belongs in, and delete what we don't need.
  • Measure first. A colleague proposed one test user per worker. We measured first: the session lock it would remove cost 1.5 % of worker time.
  • No workarounds. No workarounds in the code just to make things pass. That started a full audit of the tests.
  • The process applies. When the agent suggested an admin merge, the answer was no. Colleagues reviewed and approved every pull request.

The agent did the volume. Seven reader agents audited 81 test files, 13,181 lines and 388 tests, in about 15 minutes. It moved about 100 tests into faster layers, checked moved tests by breaking the code on purpose, ran the CI comparisons and wrote the pull requests. Some of it ran unattended, overnight and on a weekend.

The agent's mistakes, and the rules they became

The agent wrote flaky tests too. Two of its new tests used fixed 300 and 200 ms delays, a mistake it had flagged itself in an earlier review. Over the two weeks the session transcripts record about 30 mistakes: flaky tests, checks moved to the wrong layer, waits on the wrong signal, and work called done that was not.

Correcting each one was not enough, because the next test would make the same mistake. So most kinds became a rule, and so did two problems the suite had before the agent started:

The last row is the lesson. A rule the agent has to remember can be missed the day after it is written. A rule a machine checks, the lint or the CI gate, runs every time without anyone remembering it. The flaky-test gate caught the agent's own flaky test on its first run.

15 November, unattended on a quiet weekend. The agent moved three of its own tests back. The next day it wrote the rule that later slices followed.

Flaky tests that were real bugs

The surprise was how often a flaky test was not a test problem. It was a race that only showed under the timing of a loaded runner, and users could run into it too:

  • A list could show another browser tab's saved filter, because its first requests left before the tab had an id.
  • A quick pick from a menu got lost. The wait in the agent's first fix hid it; a review agent caught that.
  • An amount typed right after choosing an option could be lost, and the server answered with an error.
  • Going back to a list could show the old filter, because two requests were merged. Fixed with a failing test first; CI was green 12 minutes later.

It went the other way too. One flaky test in a colleague's pull request was a test defect only, and one import test was hardened without its root cause ever being found: 40 runs under CPU load did not reproduce it. The same lesson came up when running the PHP tests together instead of in isolation: a test that fails sometimes is a bug report until proven otherwise.

The numbers

All runs on the main branch with a test report: 131 between 1 October and 3 November, 102 between 18 and 26 November. Each pair is to scale. In that time the suite grew from about 155 to 374 tests per run.

Over the nine days after the work, 27 % of runs still had a flaky test: 0.5 flaky results per 1,000 in the first five days, 1.3 in the last four. Measured per test, flaky results fell by about three quarters while the suite more than doubled. Runs with a hard failure went from 13 % to 1 %. But 28 % of runs still went red, almost all of them because a flaky test now fails the run instead of hiding behind a retry. The median number of skipped tests per run went from 18 to 0.

My target was a suite under five minutes. In October the median run took about 4.9 minutes, for about 155 tests. Over the last nine days it took about 9 minutes, for 374. Each test runs faster than before, but the whole suite does not fit the target. Fixed waits in the suite went from 15 to 4, and the component tests from none to 386.

About 100 tests left the browser suite by 15 November: 81 to component tests, 6 to backend tests and 13 in an earlier step. Before that, 59 pixel, CSS and screenshot checks were removed; QA checks the design.

What it did not fix

Runner capacity. On 10 November the same build ran four times slower in CI than on my machine. The tests for the old screens are now a large cost: 43 % of the test time, and about half of the flaky-test incidents. That is the next problem.

What I take from it

  • The agent's mistakes are predictable. Fixed delays, waits on the wrong signal, tests that only pass on a quiet machine. Predictable mistakes can be written down as rules before they happen again.
  • A rule a machine checks beats a rule the agent remembers. The lint and the CI gate run on every change. A written note was missed the day after it was written.
  • A flaky test is a bug report until proven otherwise. Several of the ones we chased were races that users could run into.
  • "Done" needs proof. The agent called work done that was not, more than once. Every claim on this page comes from a CI run, a commit, a measurement, a ticket or the session transcripts, and the numbers say which period they cover.
