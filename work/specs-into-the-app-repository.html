Deleting a Workaround Instead of Patching It: End-to-End Tests Move Into the App Repository

A pin that tied each branch to a version of the tests broke the main branch three times. So I hardened it once, then removed the reason for it.

October – November 2026 · Test infrastructure

October to November 2026.

Two repositories, one feature

Our end-to-end tests lived in their own repository. A feature and its test could never change in the same commit, and the order of merges between the two repositories mattered. A feature merged before its test, or the other way round, and CI ran the wrong test against the right code.

The workaround: a pin

My first fix, in mid-October, was a pin: one small file in a feature branch names the branch of the test repository that CI should use. Without the file, CI used the tests' main branch as before. On the main branch, a pin was an error, so a leaked pin turned it red until someone removed it.

It worked on feature branches. It failed at merge time. On 20 October the main branch went red twice, and on 21 October again: pull requests had been merged with their pin still in. The main branch had no protection that would have stopped such a merge.

So I hardened the pin once. On the main branch it is ignored, with a notice. On any other branch, a pin it inherited from the main branch is ignored too; only a pin the branch set itself counts. Twelve new test cases cover the rules, and each rule was broken on purpose to see a test fail.

The decision: remove the reason

The hardened pin would have worked. But every rule I added made the workaround harder to understand, and the problem it worked around was still there. So I stopped patching it and removed the reason for it: the tests move into the application repository. A test then goes into the same pull request as its feature: no pin, no merge order.

The plan went into an architecture decision record first, so the team could argue with it before anything moved.

The cutover

  • One copy, at a known commit. The tests were copied from the test repository's main branch after QA had merged its last ready pull requests. CI ran from the new folder, green, before the merge.
  • Open work moves with a tool. A script and an agent skill carry an open test pull request into the new layout, screenshots included, and stop on a conflict. That part is told in Eleven Pull Requests in One Day.
  • A lint for the tests from day one. A new lint workflow checks the specs, and its five findings were fixed in the same change.

The cutover pull request, about 11,900 lines, was merged in the evening of 3 November.

The last leak, and the guard against it

On the merge day itself, three more pins reached the main branch through squash merges of branches that still carried one. A leaked pin now did real harm: the branch's own test was lost, and the main branch failed. So the next morning a pin on a feature branch became an error instead of a warning. The tests at the pin still run, so the report shows their result, but the branch cannot pass until its tests are ported. Release and hotfix branches keep their pins.

What it changed

  • A feature and its test are reviewed and merged together.
  • There is no merge order between two repositories to remember, and no pin to forget.
  • The tests could now be reorganised with the code. Moving checks into faster test layers, and later one database per test worker, both built on this.

What I take from it

  • Harden once, then question. The first failure deserved a fix. The third one deserved the question why the workaround existed at all.
  • A warning is not a guard. The pin warned for weeks. Only an error stopped the leaks.
  • The decision was mine, the volume was not. Moving the tests was a decision for a person. Porting the open work, writing the guard tests and checking every rule was the volume, and the agent did most of it.
